## 起点与已知事实

用户希望保留当前“资料跟着案例走”的创作体验。同时，平台还需要不依附某一篇案例的通用内容，包括课题组统一学习 PDF、教材和政策。用户尚未决定这些内容应叫“知识”还是统一叫“素材”，也无法仅凭文字判断管理面板。

当前源码固定于 `7afc5bb9e182b1c61827d6024670002a42937fc6`：

- 案例资料区已合并案例附件、全局素材的挂载和其他已发布案例的固定版本来源。
- 编号是引用展示顺序；正文引用保存来源身份，并在案例范围核验。`caseID + enum` 不是当前文件或资料条目的唯一键。
- 全局素材已有导入、审批、检索、下载、加入案例的代码与界面；知识已有教材目录、节正文、检索和 Agent 读取，新内容目前靠固定教材 seed，缺少通用入库管理。
- PDF 已可存储、下载；当前文件文字抽取器没有 PDF 正文读取分支。不能把“上传教材”说成“已可基于教材进行 AI 问答”。
- 仅核对源码与界面草图，未验证生产部署。

## 资料归属与待定用语

本文使用“资料”作为讨论用语。案例资料属于一篇案例的创作和引用上下文；共享资料可以独立查找、阅读、被多篇案例选用。用户已确认统一检索并保留不同归属；两类都可以有文件，文件格式不决定业务归属。最终页面名称尚未全部确定。

具体例子：

| 内容 | 候选归属 | 时间信息与适用性 |
| --- | --- | --- |
| 此次社区调研现场照片、访谈摘要 | 本案例资料 | 拍摄/调研日期，不需要假设自动过期 |
| 工程伦理教材、课题组学习 PDF | 共享资料 | 版本、出版/整理日期 |
| 政策文件 | 共享资料；案例按需引用具体版本 | 发布、生效、失效日期或被新版替代 |

案例选用共享资料后，在案例资料区保留该资料的使用记录，不要求把所有案例附件变成共享资料；移除某次使用与删掉共享资料本身是不同动作。统一检索与归属已确认，本文不构成对现有全局素材或知识数据自动迁移的授权。具体时间与适用性行为仍待讨论。

已接受的 [统一案例资料区、固定版本引用与 Word 来源清单](https://github.com/LittleDrinks/case-library/issues/158) 约束来源固定版本与下线留来源条目，不因本轮重新讨论名称而重复打开这些决定。全局素材的版本冻结实现仍有缺口，应作为实现核对事项。

## 最初的决策树与问题

- 已定：保留案例资料区的创作体验；需要案例之外的通用学习内容；管理员默认无私人内容读取权。
- 当前可问：两类内容的产品边界和名称；通用学习内容首版的使用目标。
- 等边界明确后再问：通用内容如何收录与维护、能否将案例附件显式收录、文档版本和时效状态如何展示、后台以什么视角管理。
- 等生命周期明确后再问：从案例移除、停止使用、回收、永久清理及保留期。无需用户决定对象 key、数据库集合或存储适配器。

本轮问题：

1. 保留“案例资料区”，案例外另设“知识”，知识可独立存在并被案例选用；还是希望所有资料都从统一素材库进入？建议前者，后台可提供统一盘点。

### 统一检索、选材返回与本轮实现边界

用户确认当前视觉方向，并要求保留此前版本；上一版 HTML、说明和七张截图完整存放在 [原型快照](../prototypes/archive/material-console-v1/material-console-prototype.html)，HTML 与固定提交 `aceb18360f06565fa30a9dd1176754bff6baed6d` 字节一致。

已确认产品规则：

- 统一检索教材、政策、时政新闻和案例资料，只显示当前用户有权阅读的内容；案例附件保留所属案例，共享资料可被多篇案例选用，不要求另建一个产品意义上的知识库。
- 教材、政策等共享资料由管理员维护。时政新闻属于内容类型；具体收录方式仍需继续讨论。
- “加入当前案例”全部成功后直接返回原案例资料区，看到刚加入的条目，不停留在列表展示绿色成功提示。
- 同一目标案例内，已勾选条目跨搜索、筛选和翻页保留，可逐项取消或清空；切换目标案例时清空。
- 部分成功时留在选材页，区分已加入和未加入；重试只处理未成功条目，全部成功后返回案例。
- 去掉没有真实数据来源、无助于选材的私人占用提示。这不改变管理员默认不能读取他人私人内容的已定边界。

当前源码核对：真实素材列表已在全部成功后返回 `workbench` 的 `panel=files`，但资料区内部仍默认显示附件页，需在实施时定位新加入资料；多选当前逐条提交，缺少明确的部分成功状态。素材文件仍按当前 `blobId` 读取，缺少固定文件版本；这属于已接受固定版本引用原则的实现缺口，不重新提问是否冻结。

当前原型已删除私人占用提示，实现跨搜索、筛选、翻页保留勾选，并在加入成功后直接显示案例资料区、将新资料放在前面并聚焦资料区。它仍是内存示例，只模拟全部成功；部分失败、真实 API 和持久化未实现。Chromium 检查通过；详情仍为 80% 浮窗，保留新标签页链接和原 PDF 图标。截图：[选材保留勾选](../prototypes/material-console-selection.png)、[加入后返回案例](../prototypes/material-console-case.png)。

### 资料包与正文处理

用户已确认：

- 一条资料可以包含多份文件：原 PDF、Markdown 和配套图片；检索只显示一条资料，打开后再选择文件。整组共用访问范围并一起保留版本。
- 原件保存并满足原有读取条件后先开放阅读、下载；正文独立显示待处理、处理中或失败等状态，只有准备好的正文才可供 AI 使用。
- 首版提供管理员主动调用外部 OCR 服务识别正文的入口，同时允许在其他机器解析后上传 Markdown 和图片；不要求本平台常驻小模型。此为功能范围确认，本轮没有外发任何实际资料或选择供应商。
- 原文正文与整理／解读分别标识：原文可校对识别错误，删节、改写和新增说明归为整理／解读，读者与 AI 能识别所用内容来源。
- 自动解析完成后先进入待核对；管理员确认后才供 AI 使用。在这期间原件照常可读、可下载、可选入案例。

研究见 [PDF 资料包、解析与多模态 RAG](../research/pdf-bundles-and-multimodal-rag-20261001.md)。一手来源确认：OpenDataLoader 存在扫描件 OCR 的混合模式；小米 Xiaomi-OCR-0 有官方 CPU 示例，但本服务器耗时和内存未测；阿里候选 Logics-Parsing V3 是 0.8B，官方路径使用 GPU。另有专用 OCR API，例如阿里 Qwen-OCR 接收图片、Mistral OCR 接收 PDF 并输出逐页 Markdown。没有下载模型、向外部服务发送资料或作出供应商选择。

### 同一资料的文件形态与多版次

用户澄清：资料包可能是原 PDF 加解析版 PDF，也可能想整理多个版次的《马克思主义原理》，不应提前规定为 PDF＋Markdown。讨论中的文件角色应独立于格式：原件、加文字层的可搜索 PDF、阅读正文和图片资产可以按实际内容存在；缺少 Markdown 不等于无法提取文字供 AI 使用。在线 AI 是否能读某个文件仍须经过对应读取能力和正文就绪状态验证。

新增事实：OCRmyPDF 官方明确支持为扫描 PDF 增加文字层，生成可搜索、复制文字的 PDF；这不是自动生成正确的章节或段落结构，也不是本项目已安装的能力。[官方说明](https://ocrmypdf.readthedocs.io/en/latest/introduction.html)。合集组织独立资料可以借鉴文献管理条目与合集的区分，具体采用方式仍由用户决定。[Zotero 合集模型](https://www.zotero.org/support/collections_and_tags#the_zotero_collections_model)。

“几个文件”的技术上限不是资料包的业务定义。当前优先决定同一资料身份、内容版次、多组成文档及独立资料之间的边界，再形成具体 schema。尚未创建生产 schema，也未据此修改原型的阅读默认值。
