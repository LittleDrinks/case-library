# 上海大学 VPN 访问 10.106.17.77
## 结论
上海大学公开资料无法证明 VPN 应覆盖整个 `10.106.0.0/16`。当前账号的 aTrust 会下发已授权资源的路由，但没有下发 `10.106.17.77`，因此家庭网络上的请求没有进入校园 VPN。最符合现有证据的原因是目标尚未作为 PIM 特殊资源发布给该账号，或资源关联、路由下发发生异常；不能仅凭 `10.106.*` 是私有地址判断它应由 VPN 自动覆盖。
## 官方访问模型
- 普通 VPN 用于校内业务和图书馆资源；PIM 申请的特殊端口资源明确要求使用 aTrust，并在登录后确认资源可见。
- PIM 申请按服务器 IP、端口和访问人员填写。上海大学公开的超算示例把 `10.10.22.141:22` 单独发布，审批后资源页出现该 IP；当前电脑也恰好取得该主机的 `/32` 路由。
- aTrust 采用资源级授权与 NAT 访问，不等于把校园全部私网无条件接到家庭电脑。深信服的官方排障资料也将“资源未加入隧道、未关联用户、服务端未下发路由”列为超时原因。
- `10.106.17.77` 属于 RFC 1918 私有地址，家庭运营商不会在公网转发。没有 VPN 路由时，请求只能落到家庭默认网关并超时。
## 为什么校内能连、家里 VPN 不能
校内主机位于校园网络的路由与访问控制域内，可以有到目标网段的路由；远程 VPN 是独立入口，只开放普通资源及账号获批的特殊资源。二者有不同路由和 ACL 是正常的安全边界，不代表服务器宕机。
公开资料没有上海大学内部网段、VPN 资源组和 ACL 对照表，因此无法确认 `10.106.0.0/16` 是全局排除、仅该主机未发布，还是该账号未获授权。当前路由表只能确认：本次 aTrust 会话没有覆盖目标。
## 端口 22 与 2222
改成 `2222` 不会修复缺失路由。若 PIM 只批准 `22`，改端口还会造成授权不匹配；若将 `2222` 暴露或转发到其他入口，则增加一套临时防火墙、NAT 或进程依赖，稳定性低于正式 VPN 资源。
正式结构应保持服务器 SSH 使用 `22`，由服务器负责人在 PIM 为 `10.106.17.77:22` 添加访问人员，审批后通过 aTrust 访问。只有明确存在端口冲突或安全策略要求时才改 SSH 端口，并同步修改 PIM 资源。
## 处理顺序
1. 由服务器负责人检查 PIM 中是否存在 `10.106.17.77:22`，访问人员是否包含当前账号，流程是否已审批且未因长期闲置被清理。
2. 重新登录 aTrust，确认资源页能看到目标；再检查 Windows 路由表是否出现覆盖 `10.106.17.77` 的 VPN 路由。
3. 路由仍未下发时，在 aTrust 执行“诊断修复”，将目标 IP、端口、账号、PIM 流程号和诊断结果提交企业微信“报修 12345”，或联系信息服务部 `66133370`、`66133782`。
4. 修复完成前保留 `smYuHangLab2` 作为应急跳板；不要把临时 `2222` 当作长期架构。
